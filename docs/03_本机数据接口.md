# 中南大学像素校园｜本机数据接口

**版本：** 1.0.0  
**日期：** 2026-09-26  
**状态：** 首版开发协作规范；尚未实现、启动或验收本机服务，未写入生产数据。  
**依据：** 根目录《中南大学像素校园需求文档》V0.3.2；产品待确认项继续保留，不因本接口规范而转为用户已确认。

统一类型见 [campus-v1.d.ts](contracts/campus-v1.d.ts)，首版按 Frozen 1.0.0 协作。依赖版本由 A 在初始化工程时统一锁定，本文不代表运行环境或依赖已经安装。

## 1. 服务范围与责任

D 负责本机 HTTP 服务、公共内容持久化和三个地点共用的相册能力。C 的社团活动查询及内容编辑器调用公共内容接口；B、C、D 的地点界面调用同一套相册组件和客户端。不得各自设计相册路由、错误格式或文件存储方式。

本文的服务范围仅处理两类持久数据：公共社团与活动内容、地点相册。最新需求新增的课表汇总服务不并入这两类数据，其浏览器保存、匿名快照和聚合 API 另见 [课表与社区课池](05_课表与社区课池.md)。图书馆介绍属于地点资料，不在社团活动编辑器的保存范围内。

本文定义的公共内容/相册 API 不提供课表路由；课表路由由上述独立课池协议提供。本版仍不提供照片删除、照片说明编辑、相册排序、相册备份、在线账号或远程部署能力。

## 2. 运行入口与本机约束

| 场景 | 浏览器入口 | API 服务 | 约束 |
|---|---|---|---|
| 开发联调 | `http://127.0.0.1:5173`，Vite | `http://127.0.0.1:8787`，Fastify | Vite 将 `/api` 转发给 API；启用 `strictPort`，端口占用时报错 |
| 本机验收运行 | `http://127.0.0.1:5173` | 由同一本机服务在该入口提供静态页面及 `/api` | 固定入口，不自动换端口；如明确修改配置，应同步修改访问说明和允许来源 |

服务只监听 `127.0.0.1`，不得以 `0.0.0.0` 或局域网地址代替。前端请求统一使用同源相对路径 `/api/v1/...`，组件不得硬编码 API 端口。

服务校验 Host 和写请求的 Origin，只接受配置中的本机入口；不得设置允许任意来源的 CORS。开发代理应保留浏览器来源供 API 校验。网页上传和公共内容保存只能经由已允许的本机页面发起；其他来源、缺少预期来源的浏览器写请求应明确拒绝。

访问说明统一使用上述 `127.0.0.1` 地址。不要在 `localhost`、不同端口和不同协议之间随意切换：这些入口会改变浏览器来源，从而影响个人课表的浏览器存储归属。

## 3. 固定标识和数据约定

### 3.1 地点与校区

相册只接受以下三个 `PlaceId`：

- `xiaoxiang_library`：潇湘校区图书馆。
- `xiaoxiang_teaching_group`：潇湘校区教学楼群。
- `xiaoxiang_sports_ground`：潇湘校区体育场（副场）；仅该副场具有操场交互和相册入口，体育场（鸟巢）及其他运动场不新增地点 ID 或相册。

地点名称、显示位置和互动入口调整时，ID 保持不变。教学楼群按楼座筛选课程，不改变其相册 ID。其他地图地标不能通过本接口建立场景相册。

`CampusId` 仅有 `yuelushan`、`lunan`、`xiaoxiang`。社团 `campusIds: []` 表示尚未登记适用校区；活动 `campusId: null` 表示未关联这三个校区，不得据此猜测实际校区。活动实际地点必须使用 `venue` 单独展示。

### 3.2 通用约定

- JSON 使用 UTF-8。JSON 接口的成功响应直接返回约定对象，不另套 `data` 或 `success` 包装。
- 时间字段使用带时区偏移或 `Z` 的 RFC 3339 时间字符串。活动日期筛选和展示使用 `Asia/Shanghai`，不能依赖浏览器当前时区。开始时间必须早于结束时间。
- 编辑内容均为纯文字，不存储或渲染 HTML。公开链接只接受可解析的 `http:`、`https:` 地址；空字符串不代替缺失列表。
- 社团 ID 和活动 ID 在各自集合内唯一，编辑和导出导入时保留已有 ID。活动的 `organizerClubId` 必须指向同一快照中存在的社团。
- `revision` 是公共内容快照的非负安全整数。初始化为 `0`；每次成功提交递增 `1`，失败不递增。
- 正常的空数组表示已成功读取且没有条目；读取失败、数据损坏或政策未配置不能伪装成空数据。

## 4. API 总表

| 方法与路径 | 调用方 | 请求 | 成功响应 |
|---|---|---|---|
| `GET /api/v1/capabilities` | 共用客户端、相册组件 | 无 | `200 Capabilities` |
| `GET /api/v1/public-content` | C 查询、C 编辑器 | 无 | `200 PublicContentSnapshot` |
| `PUT /api/v1/public-content` | C 编辑器 | JSON `{ expectedRevision, content: { clubs, activities } }` | `200 PublicContentSnapshot` |
| `GET /api/v1/places/:placeId/photos` | B、C、D 共用相册组件 | 固定 `placeId` | `200 { placeId, photos: PhotoMeta[] }` |
| `POST /api/v1/places/:placeId/photos` | B、C、D 共用相册组件 | 单张 multipart 图片及幂等请求头 | `201 PhotoMeta`；幂等重放同样返回 `201` 和已有结果 |
| `GET /api/v1/photos/:photoId/file` | 共用相册及大图组件 | 不透明图片 ID | `200` 图片二进制 |

不得新增另一套 `/locations` 相册路由，不得将楼座 ID 当作相册地点 ID。HTTP 路由中的地点字段统一为 `placeId`。

## 5. 能力与图片政策

`GET /api/v1/capabilities` 返回：

```ts
type Capabilities = {
  apiVersion: "v1";
  contractVersion: "1.0.0";
  placeIds: PlaceId[];
  imagePolicy: ImagePolicy;
  features: {
    photoUpload: "single";
    photoDelete: false;
    photoCaption: false;
    photoReorder: false;
  };
};

type ImagePolicy =
  | { status: "pending" }
  | {
      status: "configured";
      acceptedMimeTypes: string[];
      maxFileBytes: number;
      maxAlbumBytes: number | null;
      maxAlbumCount: number | null;
    };
```

`placeIds` 必须恰好包含第 3.1 节的三个 ID，不能因地图展示地标增加而扩展。`features` 说明当前接口支持范围；`photoUpload: "single"` 不代表上传此刻可用，仍须检查 `imagePolicy.status`。

图片格式、大小、相册容量尚未由用户确认时，正式配置保持 `pending`。相册可以继续读取已有图片，但上传按钮显示政策待配置状态；直接发起新上传应返回 `503 IMAGE_POLICY_PENDING`，不能接受所有格式或默认为无限容量。

`configured` 中，`acceptedMimeTypes` 为实际允许的非空 MIME 类型列表；字节和数量上限为正安全整数。`maxAlbumBytes`、`maxAlbumCount` 的 `null` 仅表示明确配置为不设该项上限，不能表示未知。当前规范只冻结配置形状，不填写具体格式或限额。

开发联调如需临时配置，必须在本地配置、启动提示和测试记录中标明“开发测试配置，非用户确认政策”，不能把该值写入正式验收结论。批量选择、删除、说明文字、用户排序和相册备份仍属待确认范围；本版接口不预先开放这些能力。

## 6. 公共内容读取与保存

### 6.1 数据形状

```ts
type PublicLink = { label: string; url: string };

type Club = {
  id: string;
  name: string;
  category: string;
  summary: string;
  campusIds: CampusId[];
  links: PublicLink[];
};

type Activity = {
  id: string;
  name: string;
  organizerClubId: string;
  category: string;
  startsAt: string;
  endsAt: string;
  campusId: CampusId | null;
  venue: string;
  description: string;
  links: PublicLink[];
};

type PublicContentSnapshot = {
  schemaVersion: 1;
  revision: number;
  clubs: Club[];
  activities: Activity[];
};
```

正式导出可以使用完整快照作为 JSON 备份；导入文件的 `revision` 不得用于覆盖服务器版本。C 读取并校验导入数据、展示预览后，使用当前服务器快照的 `revision` 作为 `expectedRevision` 发起 PUT。导入、导出不包含个人课表或地点图片，导出文件也不等于相册备份。

### 6.2 保存流程与冲突

1. C 先 GET 取得当前快照，编辑草稿与已保存快照分别保存。
2. C 使用 `expectedRevision` 及完整的 `clubs`、`activities` 发送 PUT。请求不接受客户端指定的新 `revision`、`schemaVersion`、图片索引或课表字段；未知字段应拒绝，避免拼错字段被静默忽略。
3. D 在同一个写入临界区检查当前版本，校验整个候选内容，再提交一个公共内容快照。社团和活动是同一个提交单位，不分别落盘。
4. 成功后返回已落盘的新快照。C 使用返回值更新查询状态并标示“保存成功”；再次进入查询界面时重新 GET，确保读到已保存内容。
5. `expectedRevision` 与当前值不同则返回 `409 REVISION_CONFLICT`。C 保留草稿，重新读取最新版并提示用户核对；不得自行换用新版号重试覆盖。

删除仍有活动引用的社团必须被整体校验阻止。用户可在同一次提交中调整或删除相关活动，再删除社团；服务不能静默删除活动或猜测替代主办社团。

首版不承诺跨浏览器实时推送；另一个浏览器刷新或重新进入查询界面后可读到新内容。GET 应避免返回陈旧的公共内容和相册索引；实现可采用 `Cache-Control: no-store`。

## 7. 相册读取、上传与图片访问

### 7.1 图片记录

```ts
type PhotoMeta = {
  id: string;
  placeId: PlaceId;
  mediaType: string;
  byteSize: number;
  createdAt: string;
  fileUrl: string;
  uploadRequestId: string;
};
```

`id` 由服务端生成；`createdAt` 使用服务端保存记录的时间；`mediaType` 使用校验后的实际图片类型，不能只相信文件扩展名或浏览器声明。`byteSize` 是已保存文件的字节数。

`fileUrl` 形如 `/api/v1/photos/{photoId}/file`，不得返回 Windows 绝对路径。`uploadRequestId` 等于该次上传的 `Idempotency-Key`，用于重复请求和断线核对；它不是账号或权限凭证。

列表只返回当前地点已完整提交的记录。空相册返回 `photos: []`。当前不承诺用户可配置的排序规则，前端按服务给出的顺序展示；不得擅自增加排序参数或管理功能。

### 7.2 单张上传与幂等

- 请求使用 `multipart/form-data`，只允许一个名为 `file` 的图片文件；多文件、缺少文件或意外文件字段返回 `400 INVALID_REQUEST`。
- 请求头必须包含 `Idempotency-Key: <UUID>`。客户端为每次新的图片上传生成一个 UUID；同一次上传在重试时复用原值，不能每重试一次就生成新值。
- 同一键、同一 `placeId`、完全相同的文件字节，返回先前已提交的 `201 PhotoMeta`，不新增文件或相册条目。用户主动再次上传同一图片，使用新键，按新上传处理。
- 同一键用于不同地点或不同文件字节时，返回 `409 IDEMPOTENCY_CONFLICT`。比较依据为服务端计算的文件内容摘要及保存的地点，不能仅比较文件名或大小。
- 幂等键、内容摘要和结果记录随相册索引一起提交，服务重启后仍能识别已完成请求；客户端看不到内部摘要或物理文件名。
- 已提交请求的幂等重放应优先返回已有结果，不因后来调整图片政策、政策待配置或达到相册容量而重复扣减容量或失败。只有经地点与字节摘要比对确认为同一次已提交请求，才适用该规则。并发收到同一键时，只能提交一次，其余请求等待该结果或明确失败，不能产生重复条目。
- 对新上传，服务检查真实图片可读取性、类型及已配置的大小和容量限制。类型声明与内容不一致或文件无法解码时明确报错，不能只按扩展名放行。
- 客户端显示上传中、保存成功或失败。只有收到已提交结果，或重新查询确认相同 `uploadRequestId` 已存在后，才显示成功。

前端不得提交目标目录、物理文件名、操作系统路径或自定 `fileUrl`。文件名和存储位置均由服务端根据固定数据目录和服务器生成的图片 ID 决定。原始文件名不作为落盘路径，不进入公共图片地址。

### 7.3 图片访问

服务通过 `photoId` 查询索引后定位文件，不将路径参数直接拼接为任意磁盘路径；未知 ID 返回 `404 PHOTO_NOT_FOUND`。仅允许读取索引中已提交的相册文件，不能将整个项目目录作为静态目录暴露。

成功响应为图片二进制，设置实际 `Content-Type` 和 `X-Content-Type-Options: nosniff`。已存在索引记录却找不到或无法读取对应文件时，应返回存储异常，不能谎报图片不存在、返回占位图或悄悄移除记录。

## 8. 错误协议与前端行为

所有 API 错误，包括文件读取路由的错误，使用相同 JSON 结构：

```ts
type ApiError = {
  error: {
    code: string;
    message: string;
    fields?: { path: string; message: string }[];
  };
};
```

`message` 是可显示给用户的说明；`fields` 用于定位具体输入错误，例如 `activities[0].endsAt`。不得在响应里返回磁盘绝对路径、异常堆栈或整段文件内容。

| HTTP 状态 | 错误码 | 主要触发条件 | 客户端行为 |
|---|---|---|---|
| `400` | `INVALID_REQUEST` | 请求结构、UUID、字段或 multipart 数量不合法 | 保留输入并提示修正 |
| `403` | `REQUEST_ORIGIN_REJECTED` | 请求来源不属于允许的本机入口 | 提示使用配置的本机入口 |
| `404` | `PLACE_NOT_FOUND` / `PHOTO_NOT_FOUND` | 不支持的地点 ID / 未登记的图片 ID | 明确提示，不创建新地点或伪造图片 |
| `409` | `REVISION_CONFLICT` | 公共内容版本已变化 | 保留草稿，读取最新版后核对 |
| `409` | `IDEMPOTENCY_CONFLICT` | 上传键被用于不同地点或内容 | 停止重试并提示请求冲突 |
| `409` | `ALBUM_LIMIT_REACHED` | 达到已配置的相册总字节或数量限制 | 保留当前相册，不提示上传成功 |
| `413` | `FILE_TOO_LARGE` | 超过已配置的单张图片大小限制 | 提示选择符合限制的图片 |
| `415` | `UNSUPPORTED_MEDIA_TYPE` | 图片实际类型不在允许列表 | 显示支持类型 |
| `422` | `INVALID_IMAGE` / `INVALID_CONTENT` | 图片损坏，或公共内容违反语义约束 | 显示原因或字段错误 |
| `503` | `IMAGE_POLICY_PENDING` | 图片政策尚未配置 | 说明待配置，保持读取能力 |
| `503` | `STORAGE_UNAVAILABLE` / `STORAGE_DATA_INVALID` | 数据目录不可用、已有文件缺失或损坏、索引引用异常 | 显示数据读取故障，不以空数据覆盖 |
| `500` | `STORAGE_WRITE_FAILED` | 写入、刷新或原子提交失败 | 保留原有有效数据和编辑草稿 |

服务网络不可达、超时、响应丢失与服务器明确拒绝不同。特别是写请求断线后，客户端不能立即断言“保存失败”或“保存成功”，应显示“保存结果未确认”。

- 公共内容：重新 GET，与待保存内容核对；如内容不一致或版本冲突，保留草稿由用户处理，不自动覆盖。
- 图片：重新 GET 当前相册，查找相同 `uploadRequestId`；已存在即确认成功。若仍未确认且原文件仍可用，使用同一幂等键和同一文件重试；不能生成新键盲目重复上传。

## 9. 文件组织与提交保护

预定运行数据目录为：

```text
data/
  public-content.json
  photos/
    index.json
    files/
```

`data` 不进入 Git，也不进入 `dist`。运行数据与地图素材、教学楼背景、源码和测试夹具分开；静态构建和更新公共内容不得清空相册。数据目录应相对于明确的项目数据根定位，不能因从不同工作目录启动而产生另一套空数据。

### 9.1 首次初始化

全新数据目录由明确的初始化流程创建合法的 `schemaVersion: 1`、`revision: 0`、空社团及活动快照，以及合法空相册索引。此初始化动作必须与“读取已有数据失败”区分。

如果已有数据文件损坏、权限不足、应存在的文件缺失或索引与文件不一致，服务报错并保留现状，不自动重置为空、不生成演示数据、不覆盖原文件。首次初始化流程不能被通用读异常处理再次触发。

### 9.2 公共内容提交

候选内容先完整校验，写入同一目录的临时文件，完成写入、必要的持久化刷新和关闭后，再以适用于当前 Windows 文件系统的原子替换方式更新有效快照。临时文件不能被 GET 当作已保存内容。

版本比较、候选校验和最终替换须处于同一串行写入流程。校验、写入或替换失败时保留旧有效快照；不得先清空旧文件再写新内容。只有提交完成后，才更新内存中对外可见的快照并返回 `200`。

### 9.3 图片及索引提交

1. 校验地点、请求头与 multipart 结构，将文件接收到暂存位置并计算实际字节数和内容摘要；暂存文件不对外可见。
2. 在串行相册写入流程中先检查幂等记录。同键、同地点、同摘要返回已有结果；同键但地点或摘要不同则返回冲突。重放不进入后续新上传政策和容量检查。
3. 仅对新上传检查政策已配置、实际图片可解码、允许类型、单张大小及当前相册容量。容量检查与最终提交处于同一串行流程，防止并发请求绕过限制。
4. 使用服务器生成的唯一名称保存图片，不覆盖已有文件。
5. 将图片记录、地点关联、幂等键、摘要和返回结果加入候选索引，完整写入临时索引后原子提交。
6. 索引提交成功后才向列表公开记录并返回 `201`。

图片已写入但索引提交失败时，旧索引和旧图片保持有效；仅对本次新产生且未关联的暂存文件进行内部清理，或保留为待恢复的孤立文件，不冒充相册成功条目。不得为了清理而删除已提交图片。

图片文件与 JSON 索引不能假装具有跨文件系统事务。崩溃发生在索引提交前时，最多留下未公开的新文件；发生在索引提交后但响应送达前时，依靠持久化的幂等记录确认结果。启动时检查索引结构及其文件关联，遇到损坏保留原始数据并报告，不静默丢弃记录。

本协议要求正常请求失败时保护原有有效数据；断电、磁盘损坏等故障的实际持久化表现仍须在实现后单独验证，不能凭接口文档宣称已通过。

## 10. 后续实现验收清单

以下均为待执行的验证要求，不是已通过记录：

- 公共内容保存后，同一应用查询界面读取新快照；重启后数据仍在。
- 无效活动时间、不存在的主办社团、冲突版本和无效导入均不破坏旧快照。
- 三个地点分别上传并读取图片；教学楼楼座筛选不切换相册。
- 相同幂等键重复、并发及重启后重试不新增图片；不同地点或内容复用同键返回冲突。
- 模拟图片落盘失败、索引提交失败、公共内容替换失败和响应丢失，确认 UI 不产生虚假成功。
- 相册空状态与存储异常明确区分；损坏 JSON 不被自动重置。
- 改变地点名称或地图入口，不改变图片关联；重启及另一浏览器能读取同一本机相册。
- 浏览器中的个人课表不进入公共内容或相册文件；三类数据更新相互隔离。
- 未支持地点、路径穿越形式的 ID、非允许来源和不符合政策的文件被拒绝，响应不泄露绝对路径。
- 端口占用时明确报错且不自动切换；浏览器始终使用已记录的固定入口。
- 图片具体格式及容量政策确认后，再补齐相应边界测试和正式预期结果。

类型定义与 [统一 TypeScript 类型契约](contracts/campus-v1.d.ts) 保持一致；如发生调整，应由接口负责人先同步契约、本文和各调用方，再改变实现。
